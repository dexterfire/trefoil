# Local servers and port forwarding

Pinned to T3 Code `v0.1.11` (`59651c1761f6c63e9b6056839067066968e6a406`). This is optional beside orchestration V2. A discovery or tunnel failure must never disconnect conversations, screens or terminals, and it affects only the environment it came from.

Discovery is read-only. Once the shell snapshot is synchronized, Trefoil opens one `subscribeDiscoveredLocalServers {}` stream per connection generation. The server requires `orchestration:read` for it (`RpcAuthorization.ts`). Each chunk replaces `ClientState.localServers` with `{servers, scannedAt}` and rows of `{host, port, url, processName?, pid?, terminal?{threadId, terminalId}, agentThreadId?}`. The server always sends `configuredUrlProbing: true`, and Trefoil ignores it. Parsing tolerates additive fields. Rows with a blank host or url, or a port outside 1..65535, are dropped. Optional fields with the wrong type read as null, and a `terminal` object counts only when it has both ids. Rows are deduped by port, and the row that names a thread wins. A chunk without a `servers` array keeps the previous list. The catalog is `live` while the stream runs. An Effect failure (an older server answers an unknown tag with `Die`) sets `supported=false`. That state shows no error and the stream is not retried during the connection. Disconnect, reconnect and environment switches clear the rows but keep `supported`.

Capability `previewTunnelSetting` (boolean, read from the server-config capabilities) becomes `ClientState.previewTunnelSetting`. It means the server honours the `enablePreviewTunnel` setting, not that the tunnel is enabled. The effective value lives in `config.settings.enablePreviewTunnel`, which managed policy may override. Trefoil does not read it yet, so a disabled tunnel shows up as a `TunnelDisabled` handshake.

Each forwarded TCP connection is one WebSocket: `GET /api/preview/tunnel?port=<remote>&wsTicket=<ticket>` on the current validated environment origin, including its current SSH loopback tunnel. It moves raw bytes both ways. Binary frames carry the data, and text frames are written to the page as UTF-8. The route requires `terminal:operate`. Tickets come from `POST /api/auth/websocket-ticket/media` (`{ticket, expiresAt}`, where expiresAt is an ISO DateTimeUtc). A media ticket lasts five minutes, is reusable and is not DPoP-bound. Trefoil therefore shares one ticket across all of an epoch's connections, refreshes it 30 s before `expiresAt` (or after 4 minutes when expiresAt can't be read), and single-flights concurrent mints. When the server refuses the ticket during a handshake, Trefoil invalidates it and retries once with a fresh one. Tickets, bearer tokens and tunnelled bytes are never logged or persisted, and ticket holders print as redacted.

Handshake classification checks T3's marker headers first. T3 sets them to exactly `1`. Any other value, such as one from a proxy, is ignored, and the status decides:
- `x-t3-tunnel-disabled: 1` gives `TunnelDisabled`.
- `x-t3-tunnel-port-refused: 1` gives `PortRefused`. At v0.1.11 it arrives as 403 when the target is the server's own port and as 502 when the dial fails.
- A 2xx without an upgrade, or a 404, gives `ServerOutdated`.
- A 401 or 403 gives `Unauthorized`.
- A transport failure, a 15 s open timeout or any other status gives `Unreachable`.

Ticket mint failures map the same way: 401/403 or a refused token renewal is `Unauthorized`, 404 is `ServerOutdated`, and anything else is `Unreachable`. A transport failure after the upgrade (the server or link drops mid-stream without a close frame) also reports `Unreachable`, and the page gets a TCP reset instead of an EOF that looks complete. Shutdowns this side starts (stop, close, the page resetting its socket) report nothing. `PortRefused` and `Unreachable` affect only that one local connection. The forward stays `Active` and keeps its listener, and its `error` is set until the next connection succeeds. `TunnelDisabled`, `ServerOutdated`, `Unauthorized` and `LocalBindFailed` end the forward: its status becomes `Failed`, its listener closes and `localPort` becomes null. A later `startPortForward` for the same port replaces a failed forward.

The forward binds both `127.0.0.1:N` and `[::1]:N` for the same N, and both listeners feed the same forwarder, so `localhost` reaches it whichever address it resolves to first and no other app's listener on the other address can answer the page. It tries the remote port number first and falls back to an ephemeral port that both addresses can bind when that port is below 1024 or busy on either, so `localUrl` (`http://localhost:N/`) is always read from the snapshot. When the device has no usable IPv6 loopback (or no shared port turned up), only IPv4 is bound and `localUrl` is `http://127.0.0.1:N/`, so no URL handed out can resolve to a listener Trefoil does not own; `PortForward.localHost` says which. Both listeners close together on every stop path, and a listener that dies while the forward is open fails the whole forward with `LocalBindFailed`. The in-app browser follows `localhost` only when the forward's URL uses it. It accepts at most 64 concurrent connections per forward, and 256 across all of a client's forwards, and closes any extra socket immediately. OkHttp 4 holds a dispatcher slot for each WebSocket's whole life, so tunnels use their own dispatcher whose request limit equals that shared admission. Admission is taken before a WebSocket is enqueued, so an upgrade never waits in OkHttp's queue or competes with the RPC socket. Upgrades are enqueued under the forward's lock, so stopping a forward also covers any upgrade in flight, and no upgrade starts after the stop. Downstream backpressure comes from OkHttp's reader thread writing straight into the local socket. Upstream sends pause while more than 1 MiB is queued, because OkHttp fails a socket past 16 MiB. When a tunnel closes, bytes already delivered are flushed and the socket is half-closed before the page sees EOF.

Half-close limit: the tunnel protocol has no half-close signal. Trefoil treats EOF from the page (a FIN, for example `shutdownOutput` after a request) as a half-close. It stops sending upstream but keeps the downstream open, so the response is delivered in full. The tunnel ends only when the remote side closes or errors, the page resets its socket, or the forward stops. A page that closes with a FIN therefore keeps its tunnel, and its admission slot, until the remote server closes the connection (HTTP servers close idle keep-alive connections; HMR WebSockets close with their own close frame). The remote server never sees the page's half-close.

Lifecycle follows screen access. Each start checks the connection generation. A forward started while the connection changes is closed and reports "Connection changed". Disconnect, failure, reconnect, environment switch and `close()` stop every forward. Forwards never restart or replay by themselves after reconnect, and the user starts them again. Ephemeral local ports are never stored as durable endpoints.

Security: any app on the device can connect to an open loopback listener while a forward is active, and it reaches the remote port with the user's `terminal:operate` authority. Forwards are therefore explicit, per port, and bound to the live connection. They stop with it and are not persisted.

The accept loop and connection lifecycle in `PortForwarding.kt` are adapted from T3 Code's MIT-licensed `SocksListener.kt` (see `T3-LICENSE.txt`). Validation uses MockWebServer WebSocket fixtures and `T3Client` session fixtures only (`PortForwardingTest`, `PortForwardSessionTest`). No real user threads or remote T3 services are touched.
